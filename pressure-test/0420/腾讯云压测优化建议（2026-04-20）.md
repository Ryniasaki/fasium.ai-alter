# 腾讯云压测优化建议（2026-04-20）

## 1. 背景

本次腾讯云 `8c16g` 极限压测结果显示：

- 稳定压测上限大约在 `14 VUs`
- `22 VUs` 左右已经明显失稳
- `28 VUs` 属于严重超载
- 主要瓶颈集中在 `tenant-service` 的请求处理和任务轮询链路

这说明当前系统不是“模型费用”限制了吞吐，而是**业务链路本身的高频轮询和数据库访问**先成为了瓶颈。

补充说明：

- 现已在腾讯云压测模式中启用 `PRESSURE_TEST_MODE=true`
- 压测模式会跳过扣费校验，但会强制要求模型相关 URL 只指向 mock
- 压测模式已切换到本地 PostgreSQL 容器，不再连接外部 PG
- 20 秒 1 VU 冒烟压测已验证任务流成功，且日志中没有出现真实外部模型域名

## 2. 优化目标

- 提高可稳定承载的 VU 上限
- 降低任务链路对 `tenant-service` 的 CPU 压力
- 减少数据库被轮询风暴打热的概率
- 保持业务流程不变，优先做低风险优化

## 3. 优化优先级

| 优先级 | 优化项 | 预期收益 | 风险/成本 |
| --- | --- | --- | --- |
| P0 | 降低轮询频率 / 改为退避轮询 | 立刻减少请求风暴 | 低 |
| P0 | 给高频只读接口加缓存 | 直接降低 CPU 和 DB 压力 | 低 |
| P1 | 把任务状态推送化（SSE / WebSocket） | 明显减少轮询压力 | 中 |
| P1 | 任务状态查询走 Redis 缓存 | 降低数据库热读 | 中 |
| P1 | 历史列表和统计接口分页/裁剪 | 减少大响应和 DB 访问 | 低 |
| P2 | 优化日志级别和日志量 | 减少高并发下的 CPU 和 IO 开销 | 低 |
| P2 | 给数据库热点表加索引 / 检查 N+1 | 提升查询效率 | 中 |
| P2 | worker 与 tenant-service 解耦扩容 | 改善资源争用 | 中 |

## 4. 重点优化方向

### 4.1 轮询机制

这是本次最核心的优化点。

当前模式是：

- 提交任务
- 频繁轮询任务状态
- 直到完成

问题：

- VU 数一上来，轮询请求会成倍放大
- `tenant-service` 会被反复打热
- 数据库和 Redis 也会跟着被拖累

建议：

- 把固定间隔轮询改成更长间隔
- 对长任务使用指数退避
- 对“几乎不会立刻完成”的状态减少查询频率
- 有条件的话改成 SSE / WebSocket / 服务端推送

### 4.2 高并发只读接口

本次压测里，只读接口 `auth/me`、`metrics`、`history` 也会成为压力源。

建议：

- `auth/me` 做短 TTL 缓存
- `metrics` 避免每次重算
- `history` 做分页和字段裁剪
- 控制返回体大小

### 4.3 数据库热读

当前腾讯云线上使用的是外部 PostgreSQL，轮询和历史查询都会直接打到数据库。

建议：

- 给状态查询和历史查询加索引
- 检查是否存在重复查询
- 将高频状态放到 Redis
- 数据库只承担最终持久化

### 4.4 日志和序列化开销

高频请求如果带很多日志，会显著放大 CPU 和 IO 压力。

建议：

- 降低高频轮询路径的日志级别
- 避免打印大对象
- 只保留必要错误日志和聚合日志

### 4.5 worker 和服务层资源争用

如果 worker 和 tenant-service 在同一台机器上竞争 CPU，那么高并发下会互相影响。

建议：

- 任务执行和任务查询尽量分离
- worker 可以考虑独立扩容
- 高峰期优先保障 tenant-service 的请求处理能力

## 5. 推荐实施顺序

### 第一阶段：低风险快速优化

1. 降低轮询频率
2. 给只读接口做缓存
3. 历史接口分页和裁剪
4. 降低日志噪音

### 第二阶段：中风险结构优化

1. 状态查询引入 Redis
2. 数据库索引和查询优化
3. worker 与查询服务资源隔离

### 第三阶段：架构级优化

1. 任务完成状态推送
2. 用 SSE / WebSocket 替代高频轮询
3. 按业务链路拆分更独立的服务

## 6. 预期效果

如果先做 P0 级优化，通常能带来最明显的收益：

- 请求失败率下降
- p95 延迟下降
- `tenant-service` CPU 明显回落
- 可稳定承载的 VU 上限提高

如果再做 P1 级优化，整体容量会继续抬升，尤其是任务流场景。

## 7. 当前结论

这次压测暴露的问题不是“机器太弱到完全不可用”，而是：

- 轮询太密
- 只读接口不够轻
- 状态查询路径过热
- 数据库热读没有隔离

所以，当前最值得先做的不是盲目加机器，而是**先减轮询、再减热读、最后再看是否需要扩容**。
