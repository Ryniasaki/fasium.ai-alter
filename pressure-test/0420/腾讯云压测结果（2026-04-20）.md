验证腾讯云线上服务器在压测模式下的业务链路稳定性，同时避免真实外部模型调用和相关费用。

## 6. 观察

1. 业务链路整体稳定，所有检查点都通过，未出现 HTTP 失败。
2. `tenant-service` 是主要 CPU 热点，说明压测主要压力集中在应用层请求处理、鉴权、任务提交和轮询逻辑上。
3. `tenant-worker`、`runninghub`、`Redis` 和 mock 服务的资源占用较低，说明当前这档压力下，瓶颈主要不在这些组件。
4. `p95` 请求延迟约 `1.04s`，在当前压测档位下是可接受的。
5. 本次压测没有触发真实外部模型调用，外部模型费用风险已被切断。

## 7. 结论

腾讯云服务器在压测模式下可以稳定支撑这档中等压力测试，核心业务链路达到 `100%` 成功率，且无真实模型费用暴露。

当前瓶颈主要集中在 `tenant-service`，后续如果继续拉高并发，优先观察：

- `tenant-service` CPU
- `tenant-service` p95 延迟
- 任务轮询和完成回收耗时
- Redis / 数据库连接和慢查询

## 9. 硬件与压力量级参考

> 下面是基于本次实测和当前项目结构给出的经验参考，前提是外部模型请求已经切到 mock，压力主要落在 `tenant-service`、数据库、Redis 和任务轮询链路上。  
> 如果切回真实 LLM / 图像模型，上限会明显下降，且不建议直接沿用下面的并发参考。

| 机器配置 | 适合的压测强度 | 典型并发参考 | 适合验证的内容 | 备注 |
| --- | --- | ---: | --- | --- |
| `4c8g` | 低压冒烟 / 功能验证 | `1-3 VUs` | 登录、只读接口、单条任务链路 | 能跑通，但容易很快碰到 CPU 拐点 |
| `8c16g` | 中压稳定测试 | `4-10 VUs` | 只读 + 改款 + 取版混合压测 | 本次实测就属于这一档，`tenant-service` 已接近 CPU 热点 |
| `16c32g` | 中高压 / 拐点探索 | `10-25 VUs` | 并发爬坡、p95 延迟、错误率、任务堆积 | 更适合找系统瓶颈和容量拐点 |
| `32c64g` 及以上 | 高压 / 容量测试 | `25+ VUs` | 峰值吞吐、极限延迟、队列积压 | 更适合做容量上限和稳定性验证 |

### 9.1 对 8c16g 的具体判断

结合本次结果，`8c16g` 在当前压测模式下的可用结论是：

- `4 VUs + 3 VUs + 3 VUs` 的混合压测可以稳定跑通
- `tenant-service` CPU 平均约 `68.94%`，峰值约 `90.87%`
- `p95` 延迟约 `1.04s`
- 成功率保持 `100%`

这意味着：

- 对于“验证链路稳定性”和“观察业务链路在中等并发下的表现”，`8c16g` 足够用
- 对于“继续大幅拉高并发”，`8c16g` 会先在 `tenant-service` 上撞到 CPU 瓶颈
- 如果目标是把并发继续推高并稳定观测，建议至少上到 `16c32g`

### 9.2 这个表怎么用

- 想做“能不能跑通”的验证：看 `4c8g`
- 想做“当前线上是否扛得住中压”：看 `8c16g`
- 想做“再往上加压会卡在哪里”：看 `16c32g`
- 想做“容量极限和稳定边界”：看 `32c64g+`

### 9.3 一个简单原则

如果你的目标负载里包含：

- 大量登录 / 鉴权
- 高频轮询
- 大量任务提交
- 任务完成后的写库和结果回收

那么优先按 `CPU` 估算容量，而不是先按内存估算。  
在当前项目里，`8c16g` 更像是“中压测试机器”，不是“高压极限机器”。
